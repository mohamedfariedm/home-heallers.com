Restrict Media Folder Visibility by Owner / Department Head تقييد ظهور ملفات الميديا حسب المالك / رئيس القسم

Project understanding, feasibility analysis and proposed design for the Dashboard “Media” area. Written against the current dev branch of the Next.js admin dashboard. فهم المشروع، وتحليل إمكانية التنفيذ، والتصميم المقترح لقسم «Media» في الداشبورد. التحليل مبني على الفرع الحالي dev من مشروع الداشبورد (Next.js).

Verdict: feasible — but it needs a backend change. A frontend-only fix would only hide files, not protect them. الخلاصة: التنفيذ ممكن — لكن لازم تعديل في الـ Backend. لو اتعمل من الفرونت فقط هيكون مجرد «إخفاء» للملفات مش حماية حقيقية. Today the whole media tree is one JSON blob inside the global site settings. It has no owner, no department, and every user downloads and re-saves the entire blob. Per-user visibility cannot be done safely on top of that structure. حاليًا شجرة الميديا كلها مخزّنة كـ JSON واحد جوه إعدادات الموقع العامة. مفيش فيها مالك ولا قسم، وكل مستخدم بيحمّل الشجرة كلها وبيحفظها كلها. عشان كده مينفعش نعمل صلاحيات لكل مستخدم فوق الهيكل ده بأمان.

Folders: the request talks about files only. The simplest consistent rule is: a folder is visible if it contains at least one visible file (or sub-folder with one), or if the viewer created it. Creators can see their own empty folders so they can upload into them.

6. Recommended design (Option A) 6. التصميم المقترح (الخيار A)

6.1 Data model6.1 نموذج البيانات

media_folders: id, name, parent_id (nullable), created_by, department_id (nullable), timestamps
media_files:   id, folder_id, name, attachment_id, attachment_original, attachment_thumbnail,
               created_by,            -- user who uploaded (set by server from the token, never from the client)
               department_id,         -- resolved by server at upload time
               timestamps
-- indexes: (created_by), (department_id), (folder_id)

created_by and department_id are written by the server from the authenticated user. The client must never send them.

created_by و department_id بيتكتبوا من السيرفر حسب المستخدم المسجّل. العميل ممنوع يبعتهم.

6.2 API6.2 الـ API

GET    /api/admin/media/tree            → folders + files, already filtered for the caller
POST   /api/admin/media/folders         { name, parent_id }
DELETE /api/admin/media/folders/{id}
POST   /api/admin/media/files           { folder_id, name, attachment }
DELETE /api/admin/media/files/{id}      → allowed for owner, dept head of file.department_id, or admin

6.3 Visibility algorithm (server)6.3 خوارزمية الظهور (على السيرفر)

visibleFile(user, file):
  if user.isAdmin                                  → true
  if file.created_by == user.id                    → true
  if file.department_id in departmentsManagedBy(user) → true   // department head
  return false

visibleFolder(user, folder):
  folder.created_by == user.id
  OR any visibleFile in folder
  OR any visibleFolder in folder.subFolders          // so the path to a visible file stays navigable

departmentsManagedBy(user) = departments where manager_id == user.id AND status == 'active'

Delete follows the same rule. Reads and deletes must both be enforced server-side.

الحذف بنفس القاعدة. القراءة و الحذف الاتنين لازم يتحكموا من السيرفر.
