Highlights (Stories) — Portable Feature Spec

A self-contained, framework-neutral specification of an Instagram-style Stories / Highlights feature, extracted from a working Laravel + Orchid implementation. Hand this to an AI or developer in another project as context. It describes what the feature does and why, the exact data model, every endpoint with real request/response shapes, and both the dashboard (admin) and mobile flows. Adapt names/stack to the target — the rules matter, not the PHP.

0. TL;DR — what we are building

  • A horizontal strip of circular avatars on the app home screen (like Instagram Stories).
  • Tapping an avatar opens a full-screen story viewer that plays that highlight's elements (image/video slides) one after another.
  • Each element may carry one CTA (Add to Cart / Open product / Open category).
  • Admins create & manage highlights from a dashboard page (not part of the mobile app).
  • The app tracks read/unread per element, per user (logged in) or per device (guest), and re-orders the strip so unread stories come first.
Naming: the feature is called Highlights everywhere in code/API. "Stories" is only colloquial. Keep one name across DB tables, API keys, and UI.

3. Business rules (the part that actually matters)

  1. Strip ordering (server-side): pinned first (by order), then unread (by order), then read last (by order). Ties by id. Instagram behavior.
  2. is_read only when every currently visible element (active + non-expired) has a view row for this viewer. Empty ⇒ not read.
  3. Adding a new element to a fully-read highlight flips it back to unread; old elements keep their views; the viewed endpoint stays idempotent for old elements. Read again only once the new element is viewed.
  4. Replacing an element's media ⇒ delete that element's view rows (new content = unviewed for everyone).
  5. is_active vs expiry are independent. Active is a manual toggle; expiry is time-based.
  6. Expiry is per element. daily: each element expires 24h after its own created_at; highlight expired when all elements expired. always never expires. Adding an element extends life (no reset timer).
  7. Max 5 elements per highlight — counts active + inactive (soft-deleted excluded).
  8. Max 3 pinned total (count excludes current on update).
  9. Branch scoping: branch_id = null ⇒ everywhere; else only that branch. Country-agnostic online branches must not let their stored country decide visibility.
  10. Country scoping: country_ids null/empty ⇒ all; else only listed. Effective country: country-id header → user home country → branch country.
  11. Image duration is a global setting highlight_image_duration_seconds (default 15, required|integer|min:1), not per element. Videos play fully.
  12. CTA payloads are embedded in the response — no second request when a CTA is tapped.
  13. Guest → user merge: an authed request carrying device_id lazily merges the device's view rows into the account (dedup on conflict). No login-endpoint change.

4. Read-state & viewer model

  • A viewer is user_id (logged in) OR device_id (guest). A written row belongs to a user (device_id=null) or a guest (user_id=null).
  • On read (home page): collect the viewer's viewed element IDs in one query, mark each element is_viewed, set highlight is_read = (all visible viewed).
  • On write (viewed endpoint): firstOrCreate the row (idempotent), return {is_read, remaining_elements} for the whole highlight so the app updates the ring without re-fetching.
  • Merge (guest→user): move rows user_id IS NULL AND device_id = X to user_id=<user>, device_id=null; if already viewed, delete the duplicate guest row.

5. Expiry model

visibility_type = always   ──►  never expires. Element shows until admin hides it.

visibility_type = daily    ──►  each element lives 24h from its OWN created_at.

   element A (created 09:00 Mon) ── visible until 09:00 Tue
   element B (created 20:00 Mon) ── visible until 20:00 Tue
   → highlight disappears from the strip only when A AND B are both expired.
   → adding element C at 08:00 Tue keeps the highlight alive until 08:00 Wed.

6. API (mobile-facing)

JSON API; auth optional on these routes. Responses wrapped as {"success":true,"data":{...}} (adapt to your envelope).

6.2 POST /api/highlights/{highlight}/elements/{element}/viewed — mark viewed

Called after each element is fully watched (image: after its duration; video: after playback ends).

  • Public route (no auth middleware). Logged-in viewer resolved from token; guest must send device_id.
  • Validates the element belongs to the highlight → 404 otherwise.
  • Idempotent — repeated calls always succeed.

Request body:

{ "device_id": "abc-123-device-uuid" }

device_id required when unauthenticated; optional (recommended once, for merge) when authed.

Response:

{
  "success": true,
  "data": { "is_read": false, "remaining_elements": 2 }
}

remaining_elements = still-unviewed visible elements; when 0, is_read is true and the app flips the ring to "seen". Errors: 404 not found; 422 missing device_id when guest.

7. Mobile app flow

  1. On home load, call GET /home_page with lat, lng, and (if available) device_id.
  2. If highlights non-empty → render the circular strip; else render the banner slider.
  3. Ring state from is_read/is_viewed: gradient ring = unread, grey = read. Server already ordered them; render as-is.
  4. Tapping opens the full-screen viewer, resuming from the first unviewed element.
  5. Image auto-advances after duration_seconds; video plays to completion.
  6. When an element finishes, call the viewed endpoint (send device_id if guest). Use returned is_read/remaining_elements to update the ring live.
  7. CTA tap uses the embedded payload — no fetch: add_to_cart → add embedded product; product_detail → open it; category → open embedded category. Any CTA closes the viewer; back must not return into it.
  8. Guest→login: keep sending device_id on at least the first authed home_page call so the server merges history (read state survives login).

8. Dashboard (admin) flow

Server-rendered pages + Ajax, gated by one permission (e.g. platform.highlights.manage), checked in every action.

8.1 Index page

Table: cover thumbnail, title, branch (or "Global"), type badge, visibility type, pinned badge, order, elements count (x/5), active toggle, expiry status badge, created_at, actions.

8.2 Create page (highlight fields only)

Elements added on the edit page after first save.

  1. visibility_type — Daily (24h) / Always
  2. branch_id — Global or a specific branch
  3. country_ids[] — none (all) or a set
  4. type — Products / Services / Both
  5. title_ar, title_en
  6. Cover image (required)
  7. is_pinned (max 3, server-validated)
  8. order (int)
  9. is_active

8.3 Edit page (fields + Elements manager)

Same fields, plus an Elements manager (Ajax CRUD, max 5). Per element:

  • media_type (image/video).
  • Media upload. Front-end validation: video duration ≤ 2 min (read via JS video.duration) and size ≤ ~150MB; image ≤ 5MB + mime. Server re-validates.
  • If video → a thumbnail image input appears.
  • cta_type (translated): None / Add to Cart / Product Detail / Category.
    • Add to Cart / Product Detail → searchable product dropdown (Ajax), filtered by highlight type, active, per-branch.
    • Category → sub-category dropdown (Ajax): subs only, active, per-branch, and (for products) only those with available products.
  • order, is_active, expired badge (daily).
Rule reminder: replacing an element's media on update ⇒ delete that element's view rows.

9. Server-side validation summary

Highlight (store/update)

  • title_ar, title_en: required strings (max 255).
  • visibility_type ∈ {daily, always}; type ∈ {products, services, both}.
  • branch_id: nullable + exists. country_ids.*: int + exists; chosen branch must belong to a selected country.
  • is_pinned: reject if already 3 pinned (excluding current).
  • cover: required on create, nullable on update; image, max 5MB.

Element (store/update)

  • media_type ∈ {image, video}.
  • media: required on create; file; video mime mp4/quicktime/webm/mkv ≤ ~150MB, image ≤ 5MB.
  • thumbnail: nullable image ≤ 5MB (video poster).
  • cta_type: nullable ∈ {add_to_cart, product_detail, category}.
  • product_id: required + exists + active when cta ∈ {add_to_cart, product_detail}.
  • category_id: required + exists (active sub-category) when cta = category.
  • Max 5 elements per highlight (counts inactive).

10. QA / acceptance checklist

  • New highlight appears first as unread; existing keep their read state.
  • Pinned + read ranks before unpinned + unread.
  • Ordering inside each group follows order.
  • is_read flips true only after all visible elements viewed.
  • Adding a 6th element rejected (including when some are inactive).
  • Adding an element to a read highlight → unread, old views intact, viewed endpoint idempotent.
  • Replacing element media wipes only that element's views.
  • Daily: element >24h disappears; highlight with all elements expired disappears; always never expires.
  • Branch scoping: global everywhere; branch highlight only in its branch.
  • Country scoping: null = all; specific list filters per resolved country.
  • Max 3 pinned enforced (excluding current on update).
  • Guest flow: views by device_id; after login with device_id, state preserved (merge), no duplicates.
  • home_page: highlights key present in guest AND logged-in paths; no other key changed.
  • Image duration setting rejects 0, negatives, empty, non-integers.
  • Permission: admin page returns 403 without the manage permission.

11. Porting notes (for the AI implementing this elsewhere)

  • Keep the three-table model and the viewer = user_id OR device_id idea; they're the backbone. Blade/Orchid/media-library are stack-specific dressing.
  • The ordering + read-state logic (§3.1–3.3, §4) is the most error-prone part — implement and test it first.
  • Return embedded CTA payloads (§3.12) so the app never makes a second call from the viewer.
  • Make the viewed endpoint idempotent from day one; the app will retry.
  • Put image duration in a global config, not per element.
  • No branch/country in your project? Drop branch_id/country_ids and treat every highlight as global — the rest is unaffected.
  • Adapt the response envelope ({success,data}) and auth scheme to the target's norms.
